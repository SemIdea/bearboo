Comparação conceitual + Q&A de discriminação. O objetivo aqui não é decorar definições — é você situar cada camada no espaço de design e nunca mais confundir integração com e2e. Tudo abaixo é ancorado nas fontes citadas; onde uma fonte não afirma algo, está marcado.

Você vê integração como "um e2e menos completo". A confusão some quando você troca o eixo: a diferença não é "quão completo", é o que cada teste valida e até onde ele vai.

  • Unit — a lógica de uma unidade, isolada. É o que você já entende.
  • Integração — a costura entre o seu código e UMA dependência externa real (o banco, sobretudo). Uma fatia do sistema, não o todo, e não pela UI.
  • E2E — o sistema inteiro pelo ponto de entrada real (browser/HTTP), como um usuário faria.

Integração e e2e diferem em escopo (uma junção vs. o sistema todo), não em completude. Um teste de integração pode ser tão pequeno em escopo quanto um unit — só que toca algo real.

A moldura é a pirâmide de testes (Fowler/Vocke), com duas regras: "write tests with different granularity" e "the more high-level you get the fewer tests you should have". Em uma frase: "Write lots of small and fast unit tests. Write some more coarse-grained tests and very few high-level tests that test your application from end to end."

Unit. O que é uma "unidade"? Fowler: em linguagem funcional, "a unit will most likely be a single function"; em OO, "a unit can range from a single method to an entire class". Duas variantes (termos cunhados por Jay Fields): solitary (troca todos os colaboradores por test doubles, isolamento total) e sociable (usa colaboradores reais, só stubando as partes lentas como banco/rede). Detalhe honesto: "unit" é mal-definido — Fowler cita um especialista que "cobre 24 definições diferentes de unit test" num treino. Dodds resume: "Verify that individual, isolated parts work as expected."

Integração. Dodds: "Verify that several units work together in harmony." Aqui mora o nó que te confunde — Fowler diz que há "(at least) two different notions of what constitutes an integration test":

  • Narrow integration test — "exercise only that portion of the code in my service that talks to a separate service", usa test doubles, e é "often no larger in scope than a unit test". O exemplo de banco é literal: "start a database, connect your application to the database, trigger a function within your code that writes data to the database, check that the expected data has been written."
  • Broad integration test — "require live versions of all services... exercise code paths through all services, not just code responsible for interactions." E o ponto que fecha a sua dúvida, nas palavras do Fowler: "If I talk about broad integration tests, I prefer to use 'system test' or 'end-to-end test.'"

Ou seja: o "e2e menos completo" que você imagina é, na verdade, o narrow. O broad é e2e — o próprio Fowler prefere não chamar de integração.

E2E. Dodds: "A helper robot that behaves like a user to click around the app and verify that it functions correctly." Por que poucos? Fowler/Vocke: e2e são "notoriously flaky and often fail for unexpected and unforeseeable reasons", exigem muita manutenção e rodam devagar — daí "you should aim to reduce the number of end-to-end tests to a bare minimum".

Software Engineering at Google (cap. 11) evita os nomes ambíguos e classifica por tamanho, porque "the most important qualities we want from our test suite are speed and determinism, regardless of the scope of the test."

  • Small — "must run in a single process"; sem I/O, rede, disco ou sleep. (≈ unit)
  • Medium — "can span multiple processes, use threads, and can make blocking calls, including network calls, to localhost", mas "aren't allowed to make network calls to any system other than localhost". (≈ integração — inclui um banco local)
  • Large — "remove the localhost restriction... allowing the test and the system being tested to span across multiple machines." (≈ e2e/sistema)

É essa definição que dissolve de vez a sua dúvida: um teste de integração ≈ um Medium test = o seu código + uma dependência real em localhost (ex.: um container Postgres). O Google mira a proporção "80% narrow-scoped unit tests, 15% medium-scoped integration tests, 5% end-to-end tests".

Onde você está hoje. O suite roda a camada domain/procedure contra prisma-mock (ADR-0011) — um fake JS sem engine SQL. Traduzindo pro vocabulário acima: os seus ~91% de cobertura backend são testes small/solitary — validam a lógica, mas o mock não é Postgres.

O buraco exato. Tudo que depende de semântica SQL real está sem teste, porque o mock não tem parser SQL — ele "mente":

  • full-text search nativo (to_tsvector/ts_rank) — o item adiado da Fase 6;
  • $queryRaw e qualquer query crua (o mock não tem parser SQL);
  • se as migrations aplicam limpo num Postgres real (o mock nunca migra).

O que é integração aqui. É o narrow integration test do Fowler / Medium test do Google: subir um Postgres real (a CI já sobe um serviço postgres:16 no job build), conectar o repositório/domain nele, exercer a query e checar o resultado. Não passa pelo browser, não sobe o app inteiro — é uma fatia código ↔ Postgres. Por isso não é "um e2e menor": é a validação dirigida de uma costura que o mock não alcança.

Por que essa ordem (unit → integração → e2e). O e2e (o "robô-usuário" clicando no app inteiro) vem por último e está adiado com o refactor de frontend — tocá-lo agora testaria uma UI que vai ser reescrita.

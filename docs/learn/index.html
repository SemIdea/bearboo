Se ler os 10 e quiser guardar uma linha: seu ErrorRegistry já resolveu "erro é dado tipado no boundary" (docs 1-3, 5, 8). O error tracer (5-a) que você quer é adicionar ao DomainError a cadeia — o campo cause tipado, preservado no boundary e navegável (docs 2, 9) — mais dois campos de metadata, severity e retryable (docs 2, 6). E a boa notícia dos docs 9-10: num monólito, "root cause" é o cause mais profundo — de graça, sem o ML que o mundo distribuído precisa.

Batch motivado pela pergunta: "o try/catch (DomainError → TRPCError) repetido em 32 lugares deveria virar uma DSL?". Os 9 resumos respondem por três eixos. Veredito costurado: não é DSL — é um helper de boundary (um adapter/anti-corruption layer in-process), e a Rule of Three já gritou pela extração da tradução (não de um framework).

Eixo DSL — o que é / quando criar:

  1. When and How to Develop DSLs (Mernik et al.) — o survey da decisão; biblioteca já é DSL fraca, e o seu caso passa 0 dos 3 testes. Comece aqui.
  2. Modular DSLs (embedding) (Hudak) — o teste da álgebra ausente: sem composição, é só uma função de ordem superior.
  3. DSL Q&A (Fowler) — interna vs. externa; fluent interface. runDomain(fn) não é DSL, é API.

Eixo Boundary — o que é / por que a tradução mora nele:

  1. Hexagonal Architecture (Cockburn) — o boundary tRPC é um adapter; a tradução é a responsabilidade dele.
  2. Anti-Corruption Layer (Evans/DDD) — o nome exato do seu boundary de erro; só tradução, nada de regra de negócio.
  3. Boundaries (Functional Core, Imperative Shell) (Bernhardt) — o erro é o valor na fronteira; log/tradução são shell.
  4. Parse, Don't Validate (King) — classifyBoundaryError é um parser; as 32 cópias são shotgun parsing.

Eixo Abstração — helper vs. camada (o discriminador):

  1. The Wrong Abstraction (Metz) — o teste que aprova runDomain e reprova o framework layers().
  2. AHA Programming (Dodds) — optimize for change first: extrair a tradução muda 32→1; o framework é YAGNI.

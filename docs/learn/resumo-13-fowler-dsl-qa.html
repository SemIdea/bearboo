Retenção-durável. Fowler é a régua prática (não acadêmica) do que conta como DSL. Lente: "o meu helper é uma DSL interna (fluent interface) ou só uma função?" — e a resposta muda o que você constrói. Recall no fim.

"Uma Domain Specific Language (DSL) é uma linguagem de programação de expressividade limitada focada num domínio específico." As três palavras que carregam tudo: limited expressiveness. Uma DSL não é Turing-completa-pra-tudo — ela faz uma coisa e é ilegível fora disso (regex, CSS, SQL). Isso é feature: o foco é o que dá a legibilidade.
  • DSL interna: "apenas um idiom particular de escrever código na linguagem host" — "frequentemente chamadas de Fluent Interfaces ou Embedded DSLs". Não há parser novo; é o seu próprio código, escrito num estilo que parece uma língua.
  • DSL externa: "uma linguagem completamente separada que é parseada em dados que a host consegue entender" (ex.: um arquivo de regras que você lê e interpreta).

A consequência prática mais importante pra você: uma DSL interna é uma forma de API — um estilo fluente de encadear chamadas. Então "isso é uma DSL?" vira uma pergunta concreta: o meu código tem um idiom encadeado/fluente que parece uma mini-língua, ou é uma chamada de função normal?

Fowler dá dois benefícios, ordenados:

  • Legibilidade → produtividade (o primário, prático): DSLs "tornam certos tipos de código mais fáceis de compreender, o que os torna muito mais fáceis de modificar, melhorando a produtividade do programador".
  • Comunicação com o negócio (secundário): "uma DSL bem projetada pode ser compreensível por pessoas de negócio, permitindo que entendam diretamente o código que implementa suas regras".

    E os custos, que ele não esconde:

    • Ferramental: "você tem que fazer uma ferramenta de edição confortável, ferramentas de debugging, de teste, e assim por diante" — sobretudo pra DSL externa.
    • Business-writable é caro: fazer o negócio escrever na DSL custa muito mais do que fazê-la legível ("business-readable... exige muito menos esforço que business-writable, mas rende a maior parte dos benefícios").

    Quando vale: "quando você olha para um aspecto do sistema com regras de negócio ricas ou workflow — uma DSL bem-escrita deve permitir que clientes entendam as regras pelas quais o sistema funciona".

    Aplique o teste do §2 direto no seu código. Uma DSL interna é um idiom fluente encadeado. Compare:

    // fluent interface (DSL interna) — parece uma mini-língua:
policy().require(role.admin).and(verified).rateLimit(5, perMinute)

// o seu caso — uma chamada de função de ordem superior:
runDomain(() => domain_recordView({ ctx, input }))

    O segundo não é uma DSL por nenhum critério de Fowler: não há encadeamento, não há idiom que "pareça uma língua", não há expressividade limitada focada num domínio — é TypeScript comum chamando uma função. É API, não linguagem. E o gancho de negócio ("regras que o cliente lê") não existe aqui: ninguém do negócio vai (nem deveria) ler a tradução DomainError→TRPCError.

    O ponto do "Semantic Model" reforça a ordem de trabalho. Na doutrina de Fowler, uma DSL é só uma fachada legível sobre um Semantic Model — a biblioteca comum que faz o trabalho de verdade. Ou seja: mesmo que um dia você quisesse a fachada fluente, você construiria a biblioteca primeiro e a DSL por cima. No bearboo essa "biblioteca" é justamente toTRPCError/runDomain. Construa o modelo semântico (o helper). A fachada fluente é opcional, posterior, e — pelo §1 — só se justifica com regras ricas que não existem num boundary de tradução.

     Fowler alerta que internal DSLs mal-feitas são piores que uma API honesta: o estilo fluente esconde o fluxo, complica o stack trace e o debugging. Um runDomain(fn) explícito preserva stack trace e leitura linear — vantagens que um builder .domain().mutation() começaria a corroer sem ganho de legibilidade correspondente. Language of limited expressiveness. Um estilo de API (fluent interface). Externa é parseada; interna é idiom da host. Legibilidade que melhora produtividade. Readable rende quase tudo por muito menos custo. Não — é API/função, sem idiom fluente.
  • DSL = linguagem de expressividade limitada focada num domínio. Interna = fluent interface (um estilo de API); externa = linguagem parseada à parte.
  • "Isso é DSL?" reduz a "tem idiom fluente encadeado?". runDomain(fn) não tem — é função, é API.
  • O valor de uma DSL é legibilidade de regras de negócio ricas; tradução de erro não é isso e ninguém do negócio a lê.
  • Toda DSL vive sobre um Semantic Model — a biblioteca real. Construa o helper (o modelo); a fachada fluente é opcional e, aqui, injustificada.

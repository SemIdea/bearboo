A sacada mais importante e contraintuitiva: "se um erro é recuperável ou não é, às vezes, contextual". O mesmo erro é fatal num lugar e tratável em outro — logo, a decisão bug-vs-recuperável do Duffy nem sempre é propriedade do erro, é propriedade do call site. Isso complica (de forma honesta) o modelo do doc 1.

Crítica-chave à string: enfiar metadata em string quebra pela Lei de Hyrum — assim que um cliente faz parse da sua mensagem de erro, mudar o texto vira breaking change. (É exatamente o anti-padrão que a regra 15 do bearboo eliminou: o front que fazia switch(error.message).)

A tese mais relevante pra você: um erro precisa carregar metadata estruturada — stack trace, severidade, caminho de validação, se é retryable — e, crucialmente, zero-ou-mais AnyError filhos (igual ao error wrapping do Go). Isso é a cadeia causal: um erro que embrulha o erro que o causou, recursivamente.

  • AnyError + AnyErrorContext: par (valor do erro, contexto key-value + call traces).
  • Call traces: stack traces, error return traces (estilo Zig — a rota de retorno do erro, não a de chamada), async stack traces.
  • Case refinement: dá pra refinar NotRepresentable em TooSmall/TooLarge sem quebrar quem só conhecia o caso genérico. Compatibilidade pra frente sem perder granularidade.
  • Unerasure: recuperar o erro fino a partir da representação grossa.

Aplicação prática citada (Kleppmann): só vale retry após erro transiente (deadlock, falha de isolamento, rede) — após erro permanente (constraint violation) retry é inútil. Ou seja: o metadata "retryable" precisa estar no tipo do erro, não na sua cabeça.

Este ensaio é praticamente a spec do que você chamou de "error tracer pica", no escopo 5-a. A estrutura AnyError = { erro, contexto, filhos[] } é o modelo de dados exato de uma cadeia causal dentro de um request. Hoje seu DomainError tem code + httpCode + message, e você já passa cause no TRPCError — mas o cause é usado só pra debug, não é estruturado nem navegável.

Evolução concreta sugerida pelo texto:

  • Dar ao DomainError um campo cause?: DomainError | Error tipado (você já aceita cause; falta tipá-lo e preservá-lo na tradução do boundary em vez de descartar).
  • Adicionar metadata no catálogo além de httpCode/message: retryable: boolean e severity — os dois campos que o texto (e o Kleppmann) dizem ser os que mais faltam.
  • No boundary, em vez de new TRPCError({..., cause: error}) e parar, preservar a cadeia: o cause do DomainError vira um elo, e o tracer caminha error.cause.cause... — a "error return trace" estilo Zig.
  • Case refinement te dá o caminho pra evoluir post.not_found em subcasos sem quebrar consumidores — resposta direta a uma dor real de catálogo que cresce.

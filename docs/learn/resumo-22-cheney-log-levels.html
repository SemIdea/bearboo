Retenção-durável + contraponto. Este é o doc que bate direto na tua tabela ErrorLevel = fatal|error|warn|info. Cheney é opinativo e minimalista — leia como provocação calibrada, não dogma.

A tese de Cheney: há só duas coisas que valem logar:

  1. "Things that developers care about when they are developing or debugging software" → nível debug;
  2. "Things that users care about when using your software" → nível info.

Todo o resto — warning, error, fatal — ele desmonta um a um. A crítica de fundo: "All logging libraries are bad because they offer too many features; a bewildering array of choice that dazzles the programmer" e distrai de pensar com clareza sobre o que comunicar ao futuro leitor dos logs.

Warning morre primeiro. "Nobody reads warnings, because by definition nothing went wrong." E colocar o nível em warning é "uma admissão de que você provavelmente está logando erros em nível warning". Ou seja, o nível é redundante — você usaria info ou error no lugar.

Error não deveria existir como nível de log. O argumento: se você logou um erro, você o tratou — então "não é mais apropriado logá-lo como erro". A regra crua: "You should never be logging anything at error level because you should either handle the error, or pass it back to the caller." (Ele distingue isso de logar sobre um erro informalmente: usar info pra anotar "não consegui abrir o arquivo foo, seguindo com plano B" é apropriado.)

Fatal só em main.main. Bibliotecas não devem usar, porque Fatal chama os.Exit(1), que impede a limpeza de defer — "semanticamente equivalente a panic". Cleanup pertence ao topo da aplicação.

Aqui está a descoberta boa: o teu modelo de erro já implementa metade do argumento de Cheney sem saber. O classifyBoundaryError (ADR-0018) divide todo erro no boundary em kind: "recoverable" | "bug". Traduz Cheney direto:

  • recoverable = o erro que você tratou (é um AppError catalogado, traduzido no boundary). Cheney diria: isso não é "error level" — é info sobre o fluxo esperado.
  • bug = o throw inesperado que ninguém tratou. Esse é o único que merece barulho. É o "error" real — e no teu logBoundaryError ele já é o único que carrega o stack completo (console.error(line, error)).

Onde Cheney te cutuca: o teu ErrorLevel tem quatro valores (fatal|error|warn|info). Pelo argumento dele, pergunte de cada um "quem age nisso?":

level do bearbooCheney perguntaria
infoOK — coisa que o usuário/operador se importa.
warn"Ninguém lê warning." Vale mesmo?
errorSe é recoverable, você tratou → não é error.
fatalSó faz sentido no topo (o teu boundary é o topo — aqui talvez sobreviva).

Isso não quer dizer "colapse pra 2 níveis já". Quer dizer: quando você desenhar a impl do logger, o kind (bug vs recuperável) provavelmente carrega mais sinal operacional do que o level de 4 valores. O bug é o teu "loud"; o resto é contexto. Vale revisitar se warn e fatal ganham o próprio lugar ou se são info/bug disfarçados.

Conceitual, pula o formalismo. O paper é teoria de categorias/equational theory densa; o que importa pra você é uma ideia que reenquadra tudo que veio antes: exception é um caso particular de algo maior. Os trechos de sintaxe abaixo são ilustrativos (estilo moderno, ex. Koka/Eff), não notação do paper de 2009.

Um algebraic effect trata operações com efeito colateral (raise, get, put, log) como operações abstratas: seu código chama a operação sem saber como ela é implementada. Quem decide o significado é um handler, depois, por fora. Separa-se declaração do efeito de interpretação dele.

effect Log { operation log(msg): void }

program() { log("start"); doWork(); log("done") }

handle program() with ConsoleHandler   // imprime
handle program() with NoOpHandler       // descarta
handle program() with CollectHandler    // acumula numa lista

O mesmo texto de programa, três significados. (Note o parentesco com a monad do doc 5: lá você troca a definição de M/★; aqui você troca o handler. Effects são a evolução dessa ideia.)

Aqui está o que faz effects serem "try/catch com esteroides". Um catch tradicional só aborta: pegou a exception, o try morreu, você não volta. Um effect handler pode retomar a computação no ponto exato da operação, entregando um resultado:

// try/catch: para, nunca retoma
try { x = risky() } catch (e) { handle(e) }

// handler: intercepta, decide, e RETOMA de onde parou
handle { x = operation() } with { op → resume(valorCalculado) }

Isso destranca backtracking, retry, non-determinism — dá pra retomar múltiplas vezes. E leva à tese que reorganiza os docs 1–5:

Exception handling é o caso particular de effect handling onde o handler escolhe NÃO retomar. throw = "efeito sem caminho de retomada". Todos os efeitos (estado, IO, exception, async) viram instâncias de um mesmo mecanismo.

Honestidade primeiro: TS não tem algebraic effects nativos, e isto não é um próximo passo prático pro bearboo. O valor aqui é enxergar o teto do espaço de design — pra você saber que existe e por que não está indo lá agora.

A conexão que vale ouro pro seu 5-a — "resume" é o retryable levado ao limite. Lembra do retryable dos docs 2 e 6? Num mundo de effect handlers, um erro transiente não seria um throw que aborta e obriga o chamador a re-executar tudo — seria uma operação que o handler retoma com o resultado do retry, sem desmontar a pilha. O "erro recuperável" do Duffy (doc 1) atinge sua forma mais pura aqui: recuperável = literalmente retomável no ponto da falha. Seu DomainError com throw está no extremo oposto (nunca retoma) — o que é ok, mas agora você sabe que "recuperável" tem gradações, e a sua é a mais grossa.

Onde isso já vaza pro seu stack, disfarçado: async/await e generators do JS são uma forma limitada de continuation/efeito (async é o efeito mais domesticado da lista). Você não vai escrever handlers algébricos, mas reconhecer que await é "um efeito cujo handler retoma quando a promise resolve" te dá o modelo mental certo. Se um dia o TS ganhar algo como effect types (há propostas), a releitura desta ideia vira prática.

 Não tente emular effect handlers com generators/callbacks no bearboo — seria complexidade sem retorno pro call depth raso que a ADR-0017 já diagnosticou. Este doc é mapa, não rota: serve pra você situar o throw/catch como o canto "não-retomável" de um espaço maior, e entender que "recuperável" é um espectro.

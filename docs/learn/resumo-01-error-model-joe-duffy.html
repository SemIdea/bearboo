Existe uma decisão de design que quase toda linguagem erra: tratar bug e erro recuperável como a mesma coisa, com o mesmo mecanismo. Duffy chama a separação dos dois de "paramount" (fundamental). São categorias com naturezas opostas:

  • Bug — condição que o programador não previu e que viola uma suposição do próprio código: null dereference, índice fora do array, invariante quebrado. Não dá pra "tratar" — o estado já é inconsistente. Resposta: abandonment (fail-fast) — derruba o processo na hora, sem rodar cleanup do usuário.
  • Erro recuperável — situação esperada do mundo: arquivo não existe, rede caiu, input inválido, credencial errada. Faz parte do contrato da função. Resposta: exceptions estaticamente checadas, que o chamador é obrigado a considerar.

A tese: use mecanismos diferentes porque as duas coisas são diferentes. Misturar (o que exceptions unchecked e error codes fazem) é a raiz da fragilidade.

Abandonment (para bugs): mata o processo imediatamente. Só é prático porque o Midori era uma rede de processos pequenos, baratos e isolados — perder um é administrável, não corrompe estado compartilhado de um monólito. "Isolation is critical." Sem isolamento, fail-fast é inviável (você derrubaria o mundo).

Checked exceptions feitas certo (para erros recuperáveis): três diferenças do Java, que é onde checked exceptions ganharam má fama:

  • O erro faz parte da assinatura da função — como um tipo. Aparece na doc, no tooltip do IDE. Você vê o que pode falhar olhando a assinatura.
  • Um único tipo de exception — sem a proliferação de throws A, B, C do Java que faz todo mundo desistir e engolir erro.
  • Análise local e modular — o compilador checa por função, não faz prova global de teorema (isso seria lento demais; ver §4).

    Error codes (C/Go):

    • Fáceis de ignorar por acidente — o valor de retorno some silenciosamente. A anedota concreta: ao portar o Microsoft Speech Server, descobriram que 80% dos requests em chinês de Taiwan (zh-tw) falhavam em silêncio por um HRESULT engolido.
    • Custo de performance "peanut butter": os if de checagem ficam espalhados ("smeared") por todo o código quente, confundindo o otimizador e queimando registradores com valores de retorno extras.

    Unchecked exceptions (Java/C#):

    • Invisíveis — nada na assinatura diz que a função lança. Controle de fluxo oculto.
    • Impossível raciocinar localmente sobre o estado durante a propagação — qualquer linha pode desviar pro topo.
    • Exceptions assíncronas (.NET) tornam operações não-atômicas.

    Benefício de perf das exceptions feitas certo: tiram o código e os dados de erro do hot path, o que melhora I-cache e TLB — o caminho de sucesso fica mais denso. É o argumento inverso do "exception é lenta": lenta é a versão unchecked com stack unwinding caro; o modelo dele paga o custo só no caminho de erro.

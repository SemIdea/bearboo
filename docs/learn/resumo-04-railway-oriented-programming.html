Entendimento por contraste. Este é o caminho que você NÃO escolheu (ADR-0017 rejeitou Result<T,E>). Ler pra entender exatamente o que abriu mão — e o que a decisão custou/economizou.

Toda função de negócio tem dois resultados possíveis: sucesso ou falha. Modele isso como dois trilhos paralelos. Uma função é um desvio (switch): entra no trilho de sucesso, pode sair no de falha. O tipo que carrega isso é o Result (a.k.a. Either): Success of 'a | Failure of 'error.

Detalhe importante que o Wlaschin faz certo e que muita gente esquece: o lado de falha carrega um tipo de erro rico, não uma string (Either [error] (value, [error]) na versão dele). Isso é o mesmo princípio da regra 15 — erro é dado estruturado, não texto.

O ganho não é o tipo, é a composição. Você encadeia funções que retornam Result e o encadeamento cuida do desvio automaticamente:

  • Short-circuit: uma vez no trilho de falha, você fica nele — as operações seguintes não rodam, o erro propaga até o fim intocado. É o equivalente funcional do "exception pula pro catch", mas explícito e sem exceptions.
  • Adaptadores pra plugar funções de tipos diferentes no pipeline:

Resultado: um pipeline validate >> canonicalize >> updateDb >> sendEmail onde qualquer passo que falhe curto-circuita o resto, e o tipo de retorno diz que pode falhar. Erro vira valor explícito na assinatura — o oposto da exception invisível (docs 1 e 3).

Wlaschin literalmente escreve: "please don't take it to extremes!" — não use ROP em todo lugar. O custo é cerimônia: toda função no pipeline precisa retornar Result, e você paga bind/map em cada junção. Ele também nota, com honestidade teórica, que "one bind does not a monad make" — ROP é a versão pragmática, não a teoria monádica completa (essa é o doc 5, Wadler).

O argumento da rejeição, agora que você viu ROP funcionando, fica cristalino. ROP paga por si quando o pipeline é PROFUNDO — muitas funções encadeadas, onde propagar erro manualmente por cada camada seria doloroso e o bind automático economiza. É o "Railway Oriented Programming (evitar poluir camadas intermediárias)" que a própria ADR cita.

No bearboo o call depth é raso: domain → 1 procedure. Não há pipeline de 6 estágios pra encadear — há uma função de domínio que lança e uma procedure que pega. Nesse formato, o bind não economiza nada (não há intermediários pra poluir), e você pagaria a cerimônia (todo domain retornando Result, toda procedure fazendo pattern-match) sem o benefício. throw DomainError + catch no boundary é menos código pro mesmo efeito. A decisão foi "o argumento do ROP não se aplica com força aqui" — e é literalmente isso.

Mas — atenção pro seu pilar 5-a: tem uma coisa que o ROP te daria de graça e que o throw não dá. No trilho de falha, o erro é um valor que você constrói e pode enriquecer a cada bind — acumular contexto ("falhou em updateDb, durante canonicalize, no request X") é natural, porque o erro passa de mão em mão explicitamente. Com throw, você ganha o stack trace de graça mas perde esse enriquecimento estruturado — o erro sobe opaco até o catch. É por isso que o seu error tracer (5-a) precisa reintroduzir manualmente, via cause, o que o Result daria automático. Você não escolheu ROP, então a acumulação de contexto causal vira trabalho explícito seu — que é exatamente o projeto do tracer.

 Não conclua "então eu deveria ter usado Result". A ADR pesou certo pro call depth atual. O gatilho pra reconsiderar seria: se surgir um fluxo de domínio genuinamente profundo (ex. uma saga de publicação com 5+ passos que podem falhar e precisam de rollback/contexto acumulado), aí o ROP localizado nesse fluxo passaria a compensar. É decisão por-fluxo, não global. Uma função que entra no trilho de sucesso e pode sair no de falha. Pluga função que-pode-falhar (1→2 trilhos) no pipeline. map é pra função que NÃO falha (1→1 trilho). Pipeline profundo; NÃO quando o call depth é raso. Call depth raso (domain→1 procedure) — bind não economiza nada. Acumulação estruturada de contexto causal (vira o cause manual).

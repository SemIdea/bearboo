Retenção-durável + transferência. Cockburn dá o nome arquitetural do que você já faz no boundary tRPC. Lente: onde a tradução DomainError→TRPCError mora, e por que ela pertence a um adapter e não espalhada. Amarra na regra dura 15 (Domain ≠ Transport). Recall no fim.

A frase-intenção: "permitir que uma aplicação seja igualmente dirigida por usuários, programas, teste automatizado ou scripts batch, e que seja desenvolvida e testada em isolamento de seus eventuais dispositivos de runtime e bancos de dados". O núcleo de negócio fica isolado das tecnologias externas — de propósito.
  • Port = uma "conversa com propósito" — uma API para um tipo específico de interação. É o o quê abstrato (ex.: "receber um comando", "persistir").
  • Adapter = a implementação específica de tecnologia que "pluga" num port, "convertendo sinais externos em chamadas de procedimento utilizáveis, e vice-versa". É o como concreto (HTTP, tRPC, Postgres, um mock).

O princípio que faz a arquitetura funcionar: o núcleo permanece "blissfully ignorant of the nature of the input device" (alegremente ignorante da natureza do dispositivo de entrada). E: "a aplicação tem uma interação semanticamente sólida com os adapters em todos os lados sem conhecer a natureza das coisas do outro lado". O adapter carrega toda a tradução específica de tecnologia — impedindo que a lógica de negócio vaze pra camada de apresentação ou de dados.

O exemplo canônico: uma mesma aplicação de cálculo de desconto, dirigida por:

  • uma GUI (interação de usuário),
  • um test harness FIT (teste automatizado),
  • uma API HTTP (comunicação entre apps),
  • um mock de banco (dev isolado) e um banco real (produção).

Cada um é um adapter diferente plugado no mesmo port. Trocar o adapter não toca o núcleo. É isso que dá testabilidade em isolamento: o teste é só mais um adapter no lugar do HTTP.

E note: isso é adapter, não DSL — Cockburn descreve conversão de sinais numa fronteira, não uma linguagem nova.

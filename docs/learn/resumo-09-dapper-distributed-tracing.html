Este é distributed tracing (pilar 5-b, entre serviços) — mas você quer o 5-a (dentro de um request). A boa notícia: o modelo de dados do Dapper é EXATAMENTE o que seu tracer 5-a precisa, menos a rede. Leio focando no que transfere pro seu caso.

Ou seja: parent id reconstrói a cadeia causal (quem causou quem) e o trace id agrupa tudo que pertence ao mesmo request. Isto é, ponto por ponto, o modelo AnyError = { erro, contexto, filhos } do doc 2 — só que Google fez pra árvore de RPCs entre máquinas.

A engenharia central: um trace context — "a small and easily copyable container of span attributes such as trace and span ids" — é carregado por toda a computação:

  • Guardado em thread-local storage enquanto uma thread processa o request.
  • Em código assíncrono/deferido, os callbacks guardam o trace context do criador e o reassociam quando executam — assim a cadeia sobrevive ao async.
  • Entre processos, o span id/trace id viajam junto no RPC.

É a distinção annotation-based vs. black-box: black-box tenta inferir a associação por regressão estatística (sem tocar no código); annotation-based marca cada registro com um id global que liga de volta ao request originador. Dapper é annotation-based, escondido em poucas bibliotecas comuns (threading, control-flow, RPC) — daí a transparência de aplicação: o dev não instrumenta nada à mão.
  • Low overhead — impacto de performance desprezível, senão os times desligam.
  • Application-level transparency — o dev não precisa saber que existe (instrumentação nas libs comuns). O mais difícil e o mais valioso.
  • Ubiquidade/escala — se não é onipresente, você perde justamente o pedaço não-monitorado onde o problema mora.

    Sampling: descoberta surpreendente — "a sample of just one out of thousands of requests provides sufficient information for many common uses". Para diagnóstico de padrões, você não precisa de todo request; precisa de amostra. (Guarde isso: o tracer que loga 100% dos requests é caro e quase sempre desnecessário.)

    Dapper (5-b)Seu tracer no bearboo (5-a)
    trace idrequest id (gere um por request no createContext)
    span / parent idcada DomainError e seu cause — a cadeia que você já tem, agora com id

    As três lições que evitam você reinventar errado:

    1. Propague um contexto pequeno, não instrumente tudo. Igual ao trace context: bote um requestId no ctx uma vez, e o erro só precisa referenciá-lo. Não saia enfiando logging em cada função de domínio (isso viola a sua própria doutrina de camadas).
    2. Transparência de aplicação é o objetivo de maior valor e o mais difícil. No seu caso, traduz pra: a captura da cadeia deve morar no boundary (onde a regra 15 já centraliza a tradução), não espalhada. Você já tem o ponto único — o catch (DomainError). É ali que o span vira registro.
    3. Sampling. Quando ligar isso em produção, não persista a árvore de todo request. Erros você quer 100% (são raros); mas se um dia adicionar tracing de sucesso (latência por camada), amostre — 1 em milhares basta pra ver padrões, como o Google achou.

    O passo concreto que sai daqui: dar ao DomainError um spanId + parentId (ou simplesmente confiar no encadeamento de cause) e um requestId vindo do ctx; no boundary, serializar a cadeia error → cause → cause… como uma árvore de spans num log estruturado. Pronto — você tem "Dapper de um processo".

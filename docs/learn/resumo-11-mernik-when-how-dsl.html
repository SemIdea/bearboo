Retenção-durável + transferência. Você (leitor sênior de prática, novato na teoria de linguagens) está decidindo se o boilerplate DomainError→TRPCError vira uma "DSL". Este é o survey acadêmico canônico da decisão. Foco: a fronteira biblioteca/embedding vs. DSL-de-verdade, e por que a resposta quase sempre é "não é DSL". Recall no fim.

Uma DSL é uma linguagem "adaptada a um domínio de aplicação específico", que oferece "ganhos substanciais em expressividade e facilidade de uso comparada com linguagens de propósito geral (GPLs) no domínio dela". O preço é explícito: DSLs trocam generalidade por expressividade num domínio limitado.

O ponto que mais importa pra sua decisão: domain-specificity é uma questão de grau, não um sim/não. Os autores põem tudo numa escala contínua — de BNF (super especializada) à esquerda até C++ (GPL) à direita, medida pelo "language level" de Jones. Alguns valores da Tabela I:

E o "level" prevê produtividade (Tabela II, em Function Points por staff-month): nível 1–3 → 5–10 FP; nível >55 → 40–100 FP. Quanto mais alto o nível de domínio, mais produtivo — mas mais caro de construir.

Aqui está o parágrafo que responde a sua pergunta quase inteira:

"Em combinação com uma application library, qualquer GPL pode agir como uma DSL. A API da biblioteca constitui um vocabulário domain-specific de nomes de classes, métodos e funções... Sendo assim, por que DSLs foram desenvolvidas? Simplesmente porque elas conseguem oferecer domain-specificity de maneiras melhores."

Ou seja: um helper nomeado (a sua API `runDomain`/`toTRPCError`) já é o degrau "application library" da escala. A pergunta não é "biblioteca ou nada" — é "a biblioteca é boa o bastante, ou o domínio precisa de mais?". Mernik dá três (e só três) razões pra uma biblioteca não bastar e valer virar DSL:

  • Notação — o domínio tem uma notação própria que a "operator notation definível pelo usuário" da GPL não alcança (ex.: regex, o infixo da matemática).
  • Construtos/abstrações que não mapeiam direto pra funções ou objetos — "traversals e error handling são exemplos típicos" que a biblioteca só expressa "de forma indireta ou desajeitada".
  • AVOPT — quando você precisa de Analysis, Verification, Optimization, Parallelization, Transformation sobre os programas do domínio, "muito mais difícil ou inviável se uma GPL fosse usada porque os padrões de código são complexos demais ou mal definidos".

    E o veredito honesto dos próprios autores: "Apesar de suas limitações, application libraries são competidoras formidáveis das DSLs. É provavelmente justo dizer que a maioria das DSLs nunca passa do estágio de application library. Essas às vezes são chamadas de domain-specific embedded languages (DSELs)."

    Desenvolver DSL tem 5 fases: decisão, análise, design, implementação, deployment. A fase de decisão é o "quando"; as outras são o "como". Os Decision Patterns (Tabela III) — as situações que justificam uma DSL — são: Notation, AVOPT, Task automation, Product line, Data structure representation, Data structure traversal, System front-end, Interaction, GUI construction.

    Sobre decidir (§2.2): "Decidir a favor de uma nova DSL geralmente não é fácil. O investimento em desenvolvimento de DSL (incluindo deployment) tem que se pagar em desenvolvimento/manutenção depois... considerações de curto prazo e falta de expertise podem facilmente causar o adiamento indefinido da decisão. Adotar uma DSL existente é muito mais barato e exige muito menos expertise do que desenvolver uma nova."

    No design (Tabela VII), a dicotomia-chave: Language exploitation (reusar uma linguagem existente — piggyback, specialization, extension) vs. Language invention (do zero). Reusar é quase sempre o certo. A lição citada de Wile é a que você deveria colar na parede:

    "You are almost never designing a programming language. [...] Corolário: Design only what is necessary. Learn to recognize your tendency to over-design." Tradução operacional: a tentação de "fazer uma linguagenzinha" é o modo de falha default de quem vem de background de design de linguagem.

    Padrões de implementação (Tabela IX): Interpreter, Compiler/application generator, Preprocessor, Embedding, Extensible compiler, COTS, Hybrid. O embedding — "construtos da DSL embutidos numa GPL host definindo novos tipos e operadores; application libraries são a forma básica de embedding" — tem vantagens/desvantagens claras:

    Vantagens do embeddingDesvantagens
    Esforço de dev modesto (reusa a implementação existente)Sintaxe longe do ótimo (host não permite sintaxe arbitrária)
    Linguagem mais poderosa — "muitas features vêm de graça"Overloading de operadores confunde se a semântica nova difere da antiga
    Infra do host reusada (editores, debuggers, tracers, profilers)Erros ruins — "mensagens em conceitos do host, não do domínio"
    Menor custo de treino (usuários já conhecem o host)Otimizações domain-specific difíceis

    O abstract fecha o argumento de custo: "DSL development is hard, requiring both domain knowledge and language development expertise. Few people have both. Não surpreende que a decisão de desenvolver uma DSL seja frequentemente adiada indefinidamente, se é que é considerada, e a maioria das DSLs nunca passa do estágio de application library."

    Passe seu caso pela grade de Mernik e ele desmorona pro lado do helper. Rode os três testes de "biblioteca não basta":

    • Notação? Não. runDomain(() => domain_recordView(...)) é chamada de função TypeScript comum — nenhuma notação nova de domínio que o TS não alcance.
    • Construto que não mapeia pra função/objeto? Não. É exatamente uma função de ordem superior (o "error handling" que Mernik cita como exemplo é justamente o que um try/catch + toTRPCError já expressa direto).
    • AVOPT? Não. Você não analisa, verifica, otimiza nem transforma "programas de tradução de erro". Não há gramática pra rodar análise em cima.

    Zero dos três. Pela própria escala do paper, o que você quer é o degrau application library / DSEL — e a frase-chave é literal: "a maioria das DSLs nunca passa desse estágio, e tudo bem". Seu toTRPCError é o "vocabulário domain-specific" (a API) que Mernik diz já ser uma DSL fraca o suficiente. Não há degrau a subir.

  • Domain-specificity é escala, não binário. Uma API nomeada já é o degrau "application library" — a DSL fraca.
  • Biblioteca só perde pra DSL em 3 casos: notação nova, construtos não-mapeáveis, ou AVOPT. O boundary de erro do bearboo não bate nenhum.
  • "You are almost never designing a programming language." O runDomain/toTRPCError é um embedding/helper — exatamente o que Mernik diz que a maioria dos casos deve ser.
  • DSL é cara (exige domínio + expertise de linguagem, "few people have both"); a decisão certa aqui é não construir linguagem.

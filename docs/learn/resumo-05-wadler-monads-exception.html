Profundo. Este é o alicerce teórico do doc 4: o bind do Railway é o ★ da exception monad do Wadler. Você não precisa de teoria de categorias (o próprio Wadler diz isso) — precisa ver onde o encanamento de erro se esconde. Uso a notação exata do paper.

Wadler abre com a tese: linguagem funcional pura tem "all flow of data made explicit" — uma bênção (modularidade máxima) e uma maldição ("the essence of an algorithm can become buried under the plumbing"). O exemplo concreto é um avaliador de expressões:

data Term = Con Int | Div Term Term · eval :: Term → Int. Direto: eval (Con a) = a; eval (Div t u) = eval t ÷ eval u. (Ex.: eval answer = 42.)

Agora adicione tratamento de erro (divisão por zero). Sem monad, você é forçado a modificar cada chamada recursiva pra checar-e-propagar:

eval (Div t u) = case eval t of
    Raise e → Raise e          -- propaga
    Return a → case eval u of
        Raise e → Raise e      -- propaga de novo
        Return b → if b == 0 then Raise "divide by zero"
                             else Return (a ÷ b)

Wadler chama isso de "straightforward, but tedious". Essa repetição de "checar o resultado e re-propagar Raise" é exatamente o encanamento que a regra 15 do bearboo eliminou no boundary — e é o mesmo que o ROP elimina com o bind.

Uma monad é uma tripla (M, unit, ★): um construtor de tipo M e duas operações que satisfazem três leis (§3 do paper). Uma função normal a → b vira a → M b — "recebe a, retorna b com um efeito possível capturado por M" (o efeito pode ser: lançar exception, estado, output…).

A leitura de m ★ λa. n é literalmente o let a = m in n — "compute m, dê o nome a ao resultado, compute n". O bind do doc 4 é este ★. Com ele, o avaliador vira:

eval (Con a) = unit a
eval (Div t u) = eval t ★ λa. eval u ★ λb. unit (a ÷ b)

A definição exata (§2.7 do paper):

data M a = Raise Exception | Return a
type Exception = String

unit a  = Return a
m ★ k   = case m of
            Raise e  → Raise e     -- ← toda a propagação mora AQUI
            Return a → k a
raise e = Raise e

Esta é a sacada inteira. Aquele case … Raise e → Raise e que estava repetido em cada chamada recursiva do §1 agora existe uma vez só, dentro do ★. O curto-circuito do trilho de falha do ROP (doc 4) é literalmente esta linha. E pra adicionar erro ao avaliador monádico, Wadler diz: "just replace unit (a ÷ b) by if b == 0 then raise "divide by zero" else unit (a ÷ b)" — uma mudança local, o resto do texto do programa não muda.

O ponto que amarra tudo: a mesma estrutura de programa serve pra exception, estado (M a = State → (a, State)) e output (M a = (Output, a)) — você só troca a definição de M/unit/★. O encanamento específico de cada efeito fica escondido no ★.

1. Você já usa a exception monad — sem chamar assim. Quando um domain faz throw new DomainError(...) e o boundary faz catch (DomainError) → TRPCError, o runtime do JS está fazendo o papel do ★: propagando o "Raise" automaticamente por você. O throw nativo é a exception monad embutida na linguagem — por isso a ADR-0017 não precisou de Result pra ter propagação automática. O JS te dá o ★ de graça via throw/catch.

2. Isso explica por que a regra 15 é a mesma ideia num nível diferente. O encanamento tedioso do §1 (re-propagar erro em cada nível) é o que você não quer espalhar. A regra 15 diz "não traduza erro em toda camada, traduza uma vez no boundary" — é o mesmo princípio de "o encanamento mora num lugar só" que motiva a monad.

3. Gancho pro 5-a — a limitação que o tracer precisa vencer. A exception monad do Wadler descarta a cadeia: Raise e → Raise e re-propaga o erro intocado. Ele não acumula "por onde passou". É a mesma perda que o doc 4 apontou no throw. Se você quisesse a cadeia causal, precisaria de uma variante onde o ★ enriquece o erro ao re-propagar (algo como Raise e → Raise (wrap contexto e)). Seu error tracer é, em essência, uma exception monad com um ★ que embrulha em vez de repassar. Ver isso na forma mínima do Wadler deixa o design do tracer nítido: é uma linha — a linha da propagação — que você quer mudar.

 Não precisa de teoria de categorias nem de reescrever nada em Haskell — Wadler é explícito que "no knowledge of category theory is required". O valor pra você é conceitual: reconhecer que throw/catch já é a exception monad, e que o encanamento de propagação é um ponto único e substituível. As "três leis da monad" (§3, não mostradas aqui) importam pra provar que o bind se comporta — não pro seu dia a dia. O algoritmo fica soterrado sob o encanamento (plumbing). Embrulha um valor puro: unit a = Return a. case: Raise→re-propaga; Return a→aplica k a. Numa linha dentro do ★ (Raise e → Raise e). O throw/catch nativo do JS — a exception monad embutida. A linha da propagação: ★ que embrulha o erro em vez de repassá-lo.
  • Monad resolve o "encanamento soterra o algoritmo": unit embrulha um valor, ★ (bind) sequencia — e esconde a propagação num lugar só.
  • Na exception monad (Raise | Return), toda a propagação de erro é uma linha dentro do ★. Adicionar erro é uma mudança local; o resto do programa não muda.
  • O throw/catch do JS já é essa monad embutida — por isso o bearboo tem propagação automática sem Result.
  • Pro 5-a: a monad clássica descarta a cadeia (re-propaga intocado). Seu tracer é a variante cujo ★ embrulha o erro ao propagar. O design cabe numa linha.

King dá a disciplina de fronteira que amarra regra 16 (validação no boundary) com a classificação de erro da feature 023 — classifyBoundaryError é, literalmente, um parser no sentido dela. Lente: traduzir/classificar UMA vez na fronteira e carregar a prova pra dentro. Recall no fim.

"A diferença entre validação e parsing está quase inteiramente em como a informação é preservada." Uma validação checa uma condição e joga o resultado fora (retorna void/bool); um parser checa a condição e retorna um tipo refinado que codifica aquele conhecimento. Definição operacional: "um parser é só uma função que consome input menos-estruturado e produz output mais-estruturado."

"Coloque seus dados na representação mais precisa que você precisa o mais cedo possível. Idealmente, isso deve acontecer na fronteira do seu sistema." Depois de parseado num tipo mais forte, o código de dentro não revalida — o type system garante o invariante. O exemplo canônico: em vez de head :: [a] -> Maybe a (validação, retorno enfraquecido), use head :: NonEmpty a -> a — fortaleça o tipo de entrada e empurre a obrigação pra fronteira onde a lista é obtida. E: "use uma estrutura de dados que torne estados ilegais irrepresentáveis."

"Shotgun parsing é um anti-padrão em que código de parsing e validação de input está misturado e espalhado pelo código de processamento." O sintoma: como a checagem se repete no meio da lógica, "erros descobertos tarde significam que dados inválidos podem já ter modificado o estado do programa", complicando a consistência. A cura é o §2: parseie uma vez, na borda.

Dois lugares onde 'parse, don't validate' já vive (ou deveria) no bearboo:

  1. O input schema (zod) da procedure é parse-no-boundary. Ele consome o request cru (menos-estruturado) e produz o input tipado (mais-estruturado); o domain_* recebe a prova e não revalida. Isso é a regra 16 dita por King — e a razão de a validação viver só no boundary da procedure.
  2. O classifyBoundaryError(error: unknown) da feature 023 é um parser textbook. Ele consome o menos-estruturado que existe (unknown — qualquer coisa lançada) e produz o mais-estruturado { kind: "recoverable" | "bug", level, retryable, code }. É exatamente "função que consome input menos-estruturado e produz output mais-estruturado". Depois desse parse, o resto do shell (o log, a resposta) não re-inspeciona o erro cru — lê o valor classificado. Perfeito.

O anti-padrão te dá o diagnóstico do boilerplate: as 26 procedures com try/catch (error instanceof DomainError) são shotgun parsing de erro — a mesma checagem/tradução "misturada e espalhada pelo código de processamento". A cura de King é a mesma da decisão helper: parseie o erro UMA vez, na fronteira (runDomain/classifyBoundaryError), e deixe o resto ler o resultado. Consolidar não é gosto estético — é remover um anti-padrão nomeado.

Gancho pro erro-como-valor (sem Result): "make illegal states unrepresentable" é a versão-tipo do que a metadata da 023 faz por convenção: quanto mais o DomainError parseado carrega kind/level/retryable como campos, menos o shell precisa re-derivar "isso é bug ou recuperável?" caso a caso. Você não foi pro Result<T,E> (decisão mantida), mas o espírito "parseie cedo, carregue a prova" você aplica via classificação na fronteira.

Profundo, mas focado no que é DISTINTO do doc 7: enquanto o Plotkin dá o mecanismo, o Leijen dá o sistema de tipos que rastreia efeitos e compila pra JavaScript. Uso a notação real do Koka do paper.

Em Koka, o tipo de uma função é τ → ε τ': recebe τ, devolve τ', e pode ter o efeito ε. O efeito é rastreado por row types (rótulos com escopo). Consequências diretas e visíveis:

Isto é "checked exceptions" (doc 1) generalizado e inferido: em vez de você declarar throws à mão (Java) e sofrer, o compilador infere quais efeitos cada função tem e propaga no tipo. A visibilidade que o Duffy queria — "olhe a assinatura e veja o que pode falhar" — cai de graça, pra todos os efeitos, não só exception.

Exception não é primitivo — é um efeito definido em biblioteca:

effect exc { raise(s: string): a }

fun safediv(x, y) { if (y == 0) then raise("divide by zero") else x / y }
// tipo inferido: (int,int) → exc int   ← o exc apareceu sozinho

O catch é um handler que descarrega o efeito — repare no tipo: entra uma ação com ⟨exc|e⟩, sai e (o exc sumiu do tipo depois do catch):

catch : (action: () → ⟨exc|e⟩ a, h: string → e a) → e a

Ou seja, o sistema de tipos sabe que depois de tratar, o erro não escapa mais. É a regra 15 do bearboo — "o erro de domínio é traduzido e não vaza além do boundary" — mas verificada pelo compilador em vez de por convenção.

O exemplo mais importante pra você. Um handler que transforma computação-que-pode-falhar em maybe (= Option/Result):

fun to-maybe(action) {
  handle(action) {
    return x  → Just(x)     // sucesso vira Just
    raise(s) → Nothing      // falha vira Nothing
  }
}   // tipo: (() → ⟨exc|e⟩ a) → e maybe⟨a⟩

Isto prova que exception e Result são intercambiáveis — um handler de 3 linhas converte um no outro. Todo o "debate" dos docs 1, 4 e 5 (throw vs. Result) se dissolve: são a mesma coisa vista por handlers diferentes. Você não precisa escolher globalmente; pode ter throw e, num ponto específico, "handleá-lo pra Option" quando quiser o estilo Result ali.

Koka compila effect handlers pra plataformas sem controle de pilha (JS, JVM, .NET) via type-directed selective CPS translation — só as partes que precisam de continuation viram CPS. E o exemplo canônico deles é async em NodeJS (§2.5): readline é modelado como efeito, e o handler registra o resume como callback do event loop. A tese: async/await é um algebraic effect — o único que o JS já domesticou com sintaxe própria.

1. A releitura da regra 15. O catch que descarrega ⟨exc|e⟩ → e é o seu boundary formalizado: o DomainError entra, o TRPCError sai, e "o domínio não vaza" vira propriedade de tipo. TS não te dá isso no compilador, mas o modelo mental — "o boundary é o handler que descarrega o efeito de erro do domínio" — é exatamente a sua arquitetura, agora com nome preciso.

2. to-maybe resolve uma tensão real sua. A ADR-0017 rejeitou Result globalmente (certo, doc 4). Mas às vezes você quer estilo-Result localmente (ex.: "tenta ler o post; se não existir, sigo com null em vez de propagar"). O to-maybe mostra o padrão: um helper tryDomain(fn): Promise<Result<T, DomainError>> que faz try/catch e converte só naquele call site. Você já fez algo parecido no recordView (o null vs. throw que discutimos). Isto te dá o vocabulário: é um handler to-maybe pontual, não uma migração global.

3. Async já é seu único efeito tipado. Toda procedure sua é async — o TS rastreia isso no tipo (Promise<T>). Você já vive num mundo onde um efeito é visível no tipo. Ver que erro poderia ser rastreado do mesmo jeito (se TS tivesse effect rows) explica por que o erro no bearboo é "invisível no tipo" hoje: falta a linha exc que o Koka teria inferido. Seu DomainError compensa isso em runtime; o tracer (5-a) é você reconstruindo à mão a informação que um effect system daria no tipo.

 Row-typed effects não existem em TS e não há como emular com honestidade (o `fp-ts`/`Effect-TS` chega perto com Effect<A, E, R>, mas é outro paradigma e pesado — fora do escopo da ADR). Leve os conceitos (efeito no tipo, handler descarrega, to-maybe converte), não a tecnologia. Se um dia avaliar Effect-TS, volte aqui — é a materialização disto em TS.

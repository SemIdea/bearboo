Varredura + entendimento. Texto curto e recente — serve pra você saber pra onde o campo convergiu e julgar se o seu ErrorRegistry está alinhado com o consenso de 2025. Conecta direto às suas rubricas (enum vs union).

Primeira convergência: C++, Java, JS, Python, C# todos chegaram no mesmo throw/catch/finally. Característica: sem marcador no call site (você não vê que a função pode falhar) e bug e erro operacional tratados igual — exatamente o pecado que o Duffy (doc 1) ataca.

Segunda convergência (a atual): Go, Rust, Swift, Zig, Kotlin, Dart convergindo em "errors as values" — erro é um valor que você retorna, não um fluxo oculto que você lança. Duas marcas registradas:

  • Marcador visível no call site: make_widget()? (Rust), widget, err := makeWidget() (Go). Você vê onde pode falhar.
  • Caminho de panic separado pra bugs: Rust/Go dão unwind recuperável via lib; Swift/Zig abortam. É a distinção bug/recuperável do Duffy virando feature de linguagem mainstream.

O coração do texto, e é a sua decisão de design:

  • Sum type (Rust enum): exaustividade total, mas composabilidade ruim entre subsistemas — pra juntar erros de módulos diferentes você sofre.
  • Tipo universal (Go error, Swift): flexível e componível, mas perde a garantia em compile-time.

Argumento decisivo — o problema "N para N+1" do Java: com throws exaustivo, adicionar uma terceira variante força atualizar a cadeia inteira. Os modelos value-oriented modernos lidam só com "0 para 1" (ou o erro está no tipo, ou não está). O autor confessa que o meio-termo é mal servido por todas as linguagens, e acha o Zig interessante (compilação closed-world + inferência entre funções infere o enum de erro pra você).

História que espelha a sua ADR: o ecossistema Rust começou com enums e migrou pra tipos universais (libs failure, depois anyhow) — porque exaustividade não escala pra cima na aplicação.

Seu ErrorRegistry é um híbrido raro e, acho, bem posicionado no meio-termo que o matklad diz ser mal servido:

  • type ErrorCode = keyof typeof Errors te dá um union fechado e exaustivo (o lado "sum type": typo no code quebra o build, você tem autocomplete do catálogo inteiro).
  • Mas DomainError é um único tipo carregando esse code (o lado "universal": você não threada AuthError | PostError | ... por toda assinatura — passa DomainError e pronto).

Ou seja: você comprou a exaustividade do enum sem pagar o custo de composabilidade do sum type, porque o namespacing (auth., post.) faz a fusão dos subsistemas ser um spread de objetos, não uma união de tipos aninhados. É exatamente a fuga do problema "N para N+1": adicionar um erro é "0 para 1" (uma entrada no objeto do domínio), não propagação em cadeia. A ADR-0017 chegou nisso por instinto de engenharia; o matklad te dá a teoria de por que foi a escolha certa.

Onde você está desalinhado com o consenso (de propósito, e tudo bem): "errors as values" quer marcador no call site. TS não tem ?-operator nem checked exceptions, então o bearboo usa throw DomainError + catch no boundary — o modelo da primeira convergência. Foi decisão consciente da ADR (call depth raso → ROP não compensa). Este texto valida que essa é uma escolha de ergonomia, não de correção — você abriu mão do marcador visível em troca de menos cerimônia, sabendo do trade.

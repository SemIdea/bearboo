Entendimento. Este é o ancestral acadêmico do seu ErrorRegistry — a ideia de que erro classificado é dado mensurável, não só uma mensagem. É o pilar mais distante do seu 5-a imediato, mas é o que transforma seu catálogo em sinal. As fontes abertas que consultei (Wikipedia, IBM Research) confirmam o conceito, os atributos e o papel do trigger, mas não enumeram os valores de "defect type" — a Wikipedia diz apenas "sete valores empiricamente estabelecidos". A lista de tipos que dou em §2 é o conjunto canônico citado pela literatura ODC, não uma transcrição do paper original (paywalled). Trato como referência, não como citação exata.

ODC "turns semantic information in the software defect stream into a measurement on the process". A ideia: em vez de contar bugs (métrica pobre) ou fazer causal analysis caso a caso (caro), você classifica cada defeito segundo atributos independentes ("ortogonais") e olha a distribuição. A distribuição vira uma assinatura do processo: onde estão os defeitos te diz em que fase o produto está e se sua verificação está funcionando — feedback durante o desenvolvimento, sem métrica externa.

"Orthogonal" = os atributos são independentes; podem ser aplicados sozinhos ou combinados pra iluminar aspectos diferentes do processo.

Cada defeito recebe atributos capturados em dois momentos:

Trigger — "the force that surfaced the fault to create the failure" (o que expôs o bug). A distribuição de triggers mede a eficácia da verificação: se um tipo de trigger só aparece tarde, sua inspeção/teste está deixando passar aquela classe de condição.

Type — a natureza do conserto. Conjunto canônico (≈7-8 valores empíricos; ver nota de fidelidade): Function, Interface, Checking, Assignment, Algorithm, Timing/Serialization, Build/Package/Merge, Documentation. A distribuição de type ao longo do tempo mede progresso: cedo domina Function (design), tarde domina Assignment/Checking (código).

ODC é sobre defeitos de desenvolvimento (bugs achados em review/teste), então não mapeia 1:1 no seu catálogo de erros de runtime. Mas a ideia transferível é forte: erro classificado com atributos ortogonais é dado mensurável, e a distribuição é uma assinatura.

Seu ErrorRegistry já tem o esqueleto disso. Cada DomainError tem um code namespaced — isso já é uma classificação. O que ODC sugere é adicionar atributos ortogonais ao catálogo e depois olhar a distribuição em produção:

  • Domínio (você já tem: auth, post, session…) — a distribuição por domínio te diz onde a dor está concentrada.
  • Type-like: o erro é validation / authz / not_found / conflict / infra? Um atributo ortogonal ao domínio — cruzar os dois é a "orthogonal" do ODC.
  • Trigger-like: o que expôs? (endpoint, role do usuário, tipo de request). Distribuição de trigger = onde sua validação de boundary está deixando passar.
  • Severity/retryable (que o doc 2 já pediu) — fecha o conjunto.

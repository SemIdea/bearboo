Retenção-durável + transferência. Hudak é o contrapeso pró-DSL do batch: mostra que, quando você de fato quer poder de linguagem, você ganha embutindo na host (reusando type system, funções de ordem superior, tools) — não inventando sintaxe. Lente: o que separa a sua tradução de erro (trivial) de um DSEL de verdade (álgebra composável). Recall no fim.

Um DSEL (domain-specific embedded language) é "uma DSL projetada dentro de uma linguagem de propósito geral existente, de ordem superior e tipada, como Haskell ou ML". A tese de abertura, em duas ideias:

  • "Nós partimos da suposição de que realmente não queremos construir uma nova linguagem do zero. Melhor: herdar a infraestrutura de alguma outra linguagem — customizando de formas específicas ao domínio de interesse — produzindo assim uma linguagem embedded domain-specific (DSEL)."
  • "Construindo sobre essa base, podemos concentrar em questões de semântica." O paper repete o slogan "semantics is more important than syntax."

    O que se reusa embutindo: "syntax, semantics, implementation code, software tools, e look-and-feel." A frase distintiva vs. abordagens de gerador de código (Jakarta etc.): "primeiro, é baseado num embedding puro — sem pré-processador, macro-expander ou gerador."

    Hudak abre com a curva de payoff (Figura 1). Duas metodologias, custo total de SW × ciclo de vida:

    • A metodologia baseada em DSL tem custo de start-up mais alto (c2 > c1) — você paga a infraestrutura na frente...
    • ...mas slope muito menor ao longo do ciclo de vida. Em algum ponto as curvas se cruzam e a DSL passa a economizar.

    O risco que ele levanta é exatamente o seu: "e se o start-up for tão alto que nunca chegamos ao break-even? Ou se erramos e pagamos o custo de start-up várias vezes durante o ciclo de vida?" A resposta do embedding: o start-up é baixo justamente porque "o esforço de desenvolvimento é modesto — uma implementação existente pode ser reusada".

    O exemplo do experimento naval (DARPA/ONR/NSWC): um DSEL de regiões geométricas. Regiões são funções:

    type Region = Point -> Bool           -- uma região é um teste de pertinência
p `inRegion` r = r p

circle  :: Radius -> Region           -- primitivas
outside :: Region -> Region           -- negação
(/\)    :: Region -> Region -> Region  -- interseção
(\/)    :: Region -> Region -> Region  -- união

annulus r1 r2 = outside (circle r1) /\ (circle r2)   -- COMPOSIÇÃO

    Repare o que faz disso uma linguagem e não só funções soltas: há uma álgebra — operadores que compõem (/\, \/, outside) e obedecem axiomas. Hudak prova a associatividade da interseção por raciocínio equacional dentro da semântica do domínio: (r1 /\ r2) /\ r3 = r1 /\ (r2 /\ r3). "O que frequentemente surge desse uso de métodos formais é uma rich algebra que captura a semântica do domínio." Funções de ordem superior "são a abstração subjacente" — não tipos de dados algébricos.

    O segundo exemplo, Fran (functional reactive animation, com a Microsoft), leva a mesma ideia a type Behavior a = Time -> a e uma álgebra de imagens (over, above, beside) que "generaliza diretamente para animações" via lifting. Uma bola pulsante é "um programa de animação extremamente conciso; o equivalente em Java tem dezenas de linhas".

    A parte "modular": construir o interpretador da linguagem por building blocks — cada feature (aritmética, chamada de função, atribuição, continuations) isolada via monad transformers, adicionada "sem alterar nenhum código anterior" (Figura 4). Isso dá evolvability: no experimento NSWC, "três versões diferentes foram desenvolvidas, cada uma capturando noções mais avançadas, sem conhecimento a priori das mudanças; a modularidade tornou essas mudanças não-triviais fáceis de incorporar."

    Mas há um preço honesto — e a lição de custo mais afiada do paper: "há um grande drawback: cada building block impõe uma camada independente de overhead interpretativo, resultando em interpretadores aparentemente impraticáveis." Cada nível de interpretação custa 15–70× de slowdown. A saída (partial evaluation) recupera performance dramaticamente:

    A moral operacional: abstração em camadas tem custo real; só compensa quando há álgebra/modularidade genuína pra amortizar (e às vezes precisa de maquinaria pesada pra pagar).

    Hudak dá o critério mais preciso de todos pro seu caso: existe álgebra? Um DSEL vale quando os construtos do domínio compõem — outside (circle r1) /\ circle r2, pic1 `over` pic2 `above` pic3. É a composição que transforma "um punhado de funções" em "uma linguagem".

    Agora olhe a sua tradução de erro. Não há nada pra compor. DomainError → TRPCError é uma seta única, terminal, sem operadores que combinem traduções entre si. Não existe traduçãoA ∘ traduçãoB, não existe axioma pra provar. Pela lente de Hudak, isso te coloca no degrau mais trivial do embedding: uma função de ordem superior (runDomain(fn)) — que é, aliás, "a abstração subjacente" que ele mesmo diz ser o motor de um DSEL. Você está usando a técnica certa (HOF na host), só que no caso onde ela colapsa pra "um helper".

    E a economia bate junto. A Figura 1 diz que embedding vence porque o start-up é baixo (reusa infra). Pro seu boundary, o "start-up" de runDomain é ~8 linhas de TS — o break-even é imediato nos 32 call-sites. Já a versão layers().domain() do test.ts começa a inventar estrutura (camadas, ctx próprio) — subindo o start-up sem álgebra que o amortize. E o drawback de Hudak te avisa: "cada camada impõe overhead"; camada sem composição a justificar é só custo.

    Cuidado de transporte: o poder dos exemplos dele vem de features que o TypeScript não tem igual — lazy evaluation (crucial pra until/=> do Fran), raciocínio equacional, type classes pro lifting automático. Não persiga uma "álgebra de erros" em TS achando que vai ganhar o que o Haskell ganha. Você tem HOF; use HOF; pare aí.

  • O que separa DSEL de "funções soltas" é uma álgebra composável (operadores que combinam + axiomas). O boundary DomainError→TRPCError não tem nenhuma.

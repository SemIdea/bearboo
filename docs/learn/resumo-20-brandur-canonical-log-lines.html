Retenção-durável. É o primeiro da coleção 3 (structured logging). Lente: o boundaryLog do bearboo loga por erro; este doc mostra o padrão oposto — uma linha larga por request. Recall no fim.

Uma canonical log line é, nas palavras do autor, "uma linha de log grande (provavelmente em logfmt) emitida no fim de um request", carregando todos os campos importantes daquele request num só lugar. Em vez de N linhas magras espalhadas pelo código ("entrou aqui", "chamou aquilo"), você emite 1 linha larga por unidade de trabalho.

Brandur a posiciona como um "tier intermediário de analytics": fica entre as métricas (rápidas, mas só respondem o que foi pré-medido) e os traces/logs crus (respondem qualquer coisa, mas com péssima relação sinal/ruído). O canonical line é o meio-termo — bom equilíbrio entre facilidade de acesso e flexibilidade de query.

O detalhe de implementação que faz o padrão funcionar: a linha é emitida no fim do request. Isso permite que cada middleware/etapa do processamento vá populando campos ao longo do request antes da emissão final. Como todos os campos-chave estão juntos numa linha, você responde quase qualquer pergunta operacional com uma única query — "quantos requests do userXYZ via TLS 1.0?" — coisa que a métrica pré-agregada não consegue.

Campos típicos que Brandur lista na linha canônica:

  • HTTP verb, path, IP de origem, user agent;
  • request IDs, status da resposta;
  • error ID e mensagem de erro;
  • API key, OAuth app e scope;
  • user ID e email;
  • nome do serviço, git revision, número de release;
  • informação de timing e dados de rate limit.

Na Stripe, as linhas iam pra dois destinos com papéis distintos:

Splunk — agregação em tempo real, query rápida, ideal durante incidentes; caro e com retenção limitada pelo volume de dados. Redshift (data warehouse) — escala, baixo custo, retenção estendida (90+ dias) e correlação cruzada entre fontes de dados. Os mesmos registros alimentavam também superfícies de produto, como o Developer Dashboard.

Tradeoffs que o próprio autor admite: menos conveniente que um dashboard pré-pronto; menos completo que os traces crus; mas o equilíbrio ótimo entre acessibilidade e flexibilidade de query.

Hoje o bearboo loga por erro, não por request. O logBoundaryError (src/shared/error/boundaryLog.ts) só dispara quando algo falha, e emite uma string no formato [kind on path] detail (ex.: [bug on post.readBySlug] session.access_token_invalid). Isso é o oposto do canonical line: você só tem sinal quando dá erro, e o sinal é prosa, não campos.

O padrão de Brandur mapeia quase 1:1 no teu stack tRPC. O withAppErrors (createRouter.ts) já é um middleware que envolve todo procedure e inspeciona result.ok — ou seja, ele já roda no fim de cada chamada, com sucesso ou erro. É literalmente o "ensure block" onde a linha canônica seria emitida. A evolução natural:

const withAppErrors = t.middleware(async ({ next, path, ctx }) => {
  const start = Date.now();
  const result = await next();

  // canonical log line: UMA por chamada, sucesso ou erro
  logger.log({
    path,                         // já disponível no middleware
    ok: result.ok,
    durationMs: Date.now() - start,
    userId: ctx.user?.id ?? null,
    kind: result.ok ? "ok" : classifyBoundaryError(result.error).kind,
    code: result.ok ? null : /* appError.code */,
    // requestId: ctx.requestId  ← próximo passo (ponte pro trace, Fase 11)
  });

  if (!result.ok) { /* tradução existente */ }
  return result;
});

Campos que você já tem: path (do middleware), kind e code (do classifyBoundaryError, ADR-0018), level (do catálogo). Faltam só durationMs, userId e um requestId — este último é a ponte pro resumo-09 (Dapper) e pra Fase 11.

 A lista de Brandur inclui user email e API key na linha. No bearboo, a regra dura 13 (tokens/segredos não vazam, agora cobrindo docs/sessions/) manda o contrário: nunca ponha token de sessão, senha ou email cru no campo. Carregue userId (opaco), não email. A canonical line é ótima — mas a régua de PII é sua, não da Stripe. Uma linha larga por request, emitida no fim. Entre métricas e logs/traces crus.

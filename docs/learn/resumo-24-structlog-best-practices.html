Retenção-durável + receita. É o lado prático da coleção: os três anteriores dão o conceito, este dá o como. Lente: vira a spec da impl do teu logger gateway (o padrão console/JSON que espelha o teu mailer transport).

A recomendação central: em produção, "you should emit structured output (like JSON) which is a lot easier to parse by log aggregators". O motivo prático: "log aggregators can render JSON much better than multiline strings" — o que melhora a análise de erro.

E o par de dev: usar "pretty printing when we run in a terminal session", mas emitir JSON quando roda em container/produção. Ou seja, mesma informação, dois renderers, escolhidos pelo ambiente.

Transporte (ecoa o 12-factor): "A simple but powerful approach is to log to unbuffered standard out and let other tools take care of the rest." O ambiente cuida do roteamento — terminal em dev, systemd/syslogd em produção, agregador do Kubernetes num cluster.

Context binding (a técnica que amarra tudo): a doc destaca a capacidade do structlog de "bind data to loggers incrementally" combinada com "loggers que são locais ao contexto de execução corrente", pra reduzir a saída a uma única entrada de log por request — seguindo, nas palavras deles, o conceito de "Canonical Log Lines" (o resumo-20!). Você liga um valor (ex: request ID) uma vez, e ele acompanha automaticamente toda entrada seguinte daquele contexto.

Recomendações concretas de destino: soluções centralizadas (ELK, Graylog) pra logs parseados, indexados e buscáveis; o formato GELF (Graylog Extended Log Format) é apontado como "an obvious choice" pra usar junto do structlog.

A técnica do structlog — ligar um requestId uma vez e ele acompanhar toda entrada do request — é o mesmo "blob no ctx" que Majors descreve (resumo-21) e a canonical line que Brandur emite (resumo-20). Um valor, ligado uma vez, presente em tudo — e é ele que vira o trace_id quando a Fase 11 trouxer OTel.
